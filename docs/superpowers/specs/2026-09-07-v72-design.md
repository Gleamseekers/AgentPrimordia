# v7.2 设计规格：基准先行 + 五命题生产级深化

> **日期**: 2026-09-07
> **版本目标**: v7.2.0
> **前置版本**: v7.1.0 GA
> **状态**: 设计中

---

## 1. 背景与动机

### 1.1 v7.1 验收结果

v7.1 为五命题（世界模型/规划增强/可观测性/工具智能/多模态）搭建了接口骨架 + 基础算法，但 6 个 A/B 实验全部未达标（McNemar p > 0.05，B 臂无统计显著增益）。

| 实验 | 配对 | A 臂 | B 臂 | 差值 | p | 门限 |
|------|------|------|------|------|---|------|
| E-1 世界模型 | 112 | 79.5% | 83.9% | +4.4pp | 0.18 | p<0.05, +15pp |
| E-4 缺口工具 | 59 | 61.0% | 49.2% | -11.9pp | 0.11 | p<0.05, +20pp |
| E-5 主动臂 | 59 | 54.2% | 52.5% | -1.7pp | 0.83 | p<0.05, +20pp |
| 多模态 | 20 | 50.0% | 45.0% | -5.0pp | — | p<0.05, +20pp |
| 工具智能 | 30 | 30.0% | 23.3% | -6.7pp | 0.56 | p<0.05, +20pp |
| 规划增强 | 1/108 | — | — | — | — | ~3h/题，中止 |

### 1.2 根因分析

1. **实现成熟度不足**：LifecycleCreator 返回占位工件、IntelligenceHook 创建工具后丢弃、规划器增加 LLM 调用但不产生有效决策
2. **Bench 设计缺陷**（已修复）：工具注册 bug、公平性 bug、纯模拟而非真实 Agent 执行
3. **根本矛盾**：bench 任务太简单（shell + filesystem 即可），B 臂的框架能力无用武之地，额外 Hook 开销反而消耗 token 预算

### 1.3 v7.2 方向决策

V7 弧线的宏大叙事（世界模型/蒸馏/结社）与现实脱节。v7.2 回归务实工程深化：

- **骨架 → 生产级实现**：把 v7.1 的接口骨架变成真正可用的生产级代码
- **通用基准驱动**：不绑定具体应用，用通用硬基准任务驱动框架进化
- **接线与集成**：聚焦把已有能力真正接线打通，而非新增能力

## 2. 硬任务集设计

### 2.1 设计原则

硬任务集必须满足一个硬约束：**A 臂（纯 ReAct + 基础工具）无法可靠完成，B 臂（启用框架能力）有结构性优势**。

入选标准：用纯 ReAct + shell/filesystem 预筛，成功率 < 60% 才入选。

### 2.2 各命题硬任务特征

#### P1 世界模型（≥30 道）

任务状态不可从当前上下文直接推断，需要维护实体/关系状态图：

- 多步状态追踪（"第三个文件的作者是否和第一个文件的编辑者是同一人？"）
- 因果链推理（"如果修改 A 文件，哪些下游文件需要同步更新？"）
- 实体关系变化检测（"经过这 5 步操作后，项目依赖图发生了什么变化？"）

#### P2 规划增强（≥30 道）

≥5 步有依赖关系的子任务，含条件分支和失败回退：

- 多阶段数据处理 pipeline（下载→清洗→转换→验证→聚合）
- 中间步骤可能失败需重规划的任务
- 资源约束下的多目标优化任务

#### P4 工具智能（≥30 道）

任务所需工具不在预置工具集中，Agent 必须检测缺口→创建→使用：

- 需要特定格式转换器的任务（预置工具只有 shell/filesystem，没有 JSON→CSV 转换器）
- 需要特定分析器的任务（预置工具无法做代码复杂度分析，需自动创建）
- 需要特定生成器的任务（预置工具无法做模板渲染，需自动创建）

#### P5 多模态（≥30 道）

任务输入包含图片/图表，纯文本无法获取关键信息：

- 图表数据提取（给定折线图/柱状图图片，提取数据点）
- UI 截图分析（给定界面截图，识别布局问题）
- 图片中文字 OCR + 推理（给定手写笔记图片，结构化提取内容）

#### P3 可观测性（改为集成测试验收）

不适合 A/B 实验，改为端到端集成测试：

- 启动 Agent → 跑任务 → 验证 OTel 导出 → 验证告警触发 → 验证 Dashboard 渲染

### 2.3 任务注册与冻结

- 所有任务注册进 `docs/evals/v72/`，含 manifest sha256 哈希
- 冻结后不可修改（`TestEvalRegistryFrozen` 门控）
- ≥30% 任务为留出集（开发期不可见）

## 3. 五命题生产级深化

### 3.1 P1 世界模型深化

**v7.1 现状**：状态图内核存在（`internal/agent/worldmodel/`），但未真正接入 ReAct 决策循环。

**v7.2 深化目标**：

| 能力 | 实现内容 | 接线点 |
|------|---------|--------|
| 状态图自动构建 | Agent 执行任务时自动从工具调用结果提取实体/关系，更新状态图 | `react_loop.go` 的 tool result 处理路径 |
| Model-based 预演 | 行动前在状态图上模拟后果，选择最优行动 | action selection 阶段消费世界模型状态 |
| 回溯校验 | 行动后对比预期 vs 实际，差异进失败库 | tool result 回传后触发校验 |

**关键文件**：`internal/agent/worldmodel/`、`internal/agent/react_loop.go`

### 3.2 P2 规划增强深化

**v7.1 现状**：EnhancedPlanner 存在但 ~3h/题（太多 LLM 调用），DeadlockDetector/ApprovalGate 是空壳。

**v7.2 深化目标**：

| 能力 | 实现内容 | 接线点 |
|------|---------|--------|
| 规划缓存 | 相似任务复用已有 plan 骨架，减少 LLM 调用 | `EnhancedPlanner.Decompose` 前置缓存查询 |
| 轻量 replan | 只在执行偏差超阈值时触发 LLM replan | `ManagedPlan` 状态机增加偏差检测 |
| DeadlockDetector 真实化 | 检测连续 N 次相同工具+相同参数 → 触发恢复策略 | `react_loop.go` 的 turn 间检测 |

**关键文件**：`internal/agent/planning/`、`internal/agent/react_plan_executor.go`

### 3.3 P4 工具智能深化

**v7.1 现状**：LifecycleCreator 生成 shell 脚本，但缺口检测→创建→注册→使用链路不流畅。

**v7.2 深化目标**：

| 能力 | 实现内容 | 接线点 |
|------|---------|--------|
| GapDetector 真实化 | 基于工具调用 trace 的统计分析（高频失败模式 = 缺口） | `IntelligenceHook.AfterToolCall` 记录 → `OnTurnEnd` 分析 |
| Creator 升级 | 基于 LLM 的工具生成（给定缺口描述 + 示例输入输出，生成脚本） | `LifecycleCreator.Create` 接入 LLM |
| 自动注册 + 发现 | 创建的工具自动进 Registry，后续 turn 自动被 Agent 发现使用 | `registeringCreator` 正式化进框架 |

**关键文件**：`internal/tools/intelligence/`、`internal/tools/intelligence/create/`、`internal/agent/react_loop_tools.go`

### 3.4 P5 多模态深化

**v7.1 现状**：ContentPart 抽象存在，但 sensenova 文本模式已足够处理 bench 任务。

**v7.2 深化目标**：

| 能力 | 实现内容 | 接线点 |
|------|---------|--------|
| 真实多模态 Provider | 支持图片输入的 LLM 调用（sensenova/OpenAI vision） | `internal/llm/openai_provider.go` 增加 vision 路径 |
| 图片理解工具链 | 内置 OCR、图表解析、UI 分析工具 | `internal/tools/builtin/` 新增 multimodal 工具组 |
| 消息直传 | ReAct 循环的 user message 支持多模态 ContentPart 直传 Provider | `react_loop.go` 的 message 构建路径 |

**关键文件**：`internal/agent/multimodal/`、`internal/llm/openai_provider.go`

### 3.5 P3 可观测性（集成测试验收）

**v7.2 深化目标**：

| 能力 | 实现内容 | 验收方式 |
|------|---------|---------|
| OTel 真实导出 | ReAct 循环的 trace/span 真实发送到 OTLP endpoint | 集成测试：启动 Agent → 验证 OTel 收到数据 |
| 告警引擎接线 | 延迟/错误率超阈值 → 真实触发告警（日志/webhook） | 集成测试：注入慢请求 → 验证告警触发 |
| Dashboard 真实数据 | HTTP handler 返回真实运行指标 | 集成测试：GET /dashboard → 验证非空数据 |

**关键文件**：`internal/observability/`、`internal/otel/`

## 4. 阶段节奏

### 4.1 三阶段总览

| 阶段 | 时间盒 | 交付物 |
|------|--------|--------|
| S1 硬任务集 | 2 周 | 4 命题 × ≥30 道硬任务，注册冻结 `docs/evals/v72/`，A 臂预筛 <60% |
| S2 生产级实现 | 6-8 周 | 五命题深化代码，每命题完成接线后即时 smoke bench |
| S3 验收 | 2 周 | 改良 A/B 跑硬任务集 + P3 集成测试全过 |

**总工期**：10-12 周

### 4.2 S2 内部节奏

按依赖关系分两波：

**第一波（前 4 周）**——基础层：
- P4 工具智能（链路最长，GapDetector→Creator→Registry→Agent 全通）
- P2 规划增强（规划缓存 + 轻量 replan + deadlock 真实化）
- P3 可观测性（OTel 接线 + 告警 + Dashboard，独立无依赖）

**第二波（后 2-4 周）**——依赖第一波：
- P1 世界模型（需要 P2 的规划器消费状态图）
- P5 多模态（需要 Provider 层改造，独立于其他命题）

## 5. 验收策略

### 5.1 双层验收

1. **地板**：每个命题的端到端集成测试全过（证明能力可用）
2. **天花板**：改良 A/B 在硬任务集上跑 McNemar 检验（证明能力有增益）

### 5.2 A/B 改良点

吸取 v7.1 教训：

- 任务集替换为硬任务（A 臂预筛 <60% 才入选）
- B 臂 token/轮次预算适当放宽（给框架能力发挥空间）
- 每个实验 N 按 R2 功效计算重新定（不拍脑袋）
- bench 运行器复用 v7.1 已修复的版本（工具注册、公平性、真实 Agent 执行）

### 5.3 验收门限

| 命题 | 门限 | 备注 |
|------|------|------|
| P1 世界模型 | McNemar p<0.05, +≥15pp | 沿用 V7 路线图 R2 |
| P2 规划增强 | McNemar p<0.05, +≥15pp | 沿用 V7 路线图 R2 |
| P4 工具智能 | McNemar p<0.05, +≥20pp | 沿用 V7 路线图 R2 |
| P5 多模态 | McNemar p<0.05, +≥20pp | 沿用 V7 路线图 R2 |
| P3 可观测性 | 端到端集成测试全过 | 改为集成测试验收 |

## 6. 风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| API key 余额不足 | 沿用降级豁免机制，充值即自动复活 |
| 硬任务集设计不出有效的硬任务 | A 臂预筛机制兜底，确保入选任务确实需要框架能力 |
| 生产级实现工作量超预期 | S2 分两波推进，第一波完成后评估是否裁剪第二波范围 |
| 规划增强仍然太慢 | 规划缓存 + 轻量 replan 双管齐下，smoke bench 即时验证 |

## 7. 与 V7 路线图的关系

v7.2 不改变 V7 弧线的铁律与治理规则（R1-R4 沿用），但在方向上做了务实调整：

- V7 路线图的原版叙事是「具模→内化→开源→长活→结社→大成」
- v7.1 实际落地为「五命题接口骨架」
- v7.2 定位为「五命题生产级深化」，是 v7.1 的自然延续
- 验收达标后，v7.2 GA 正式关闭 V7 弧线的命题验收项
