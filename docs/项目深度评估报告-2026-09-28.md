## 四、深度发现

### 4.1 🔴 P0 — 安全实证（7 条攻击链 + 2 个并发/健壮性 P0）

#### P0-1 默认 Shell 工具白名单可绕过 → 宿主任意代码执行

`internal/tools/builtin/shell.go` 的 `NewShell()` **默认开启白名单模式**，且 `DefaultToolkit`（README 快速入门推荐用法）注册 Shell 时**不注入 Sandbox**。评估开始时仓库内遗留两个未跟踪的安全验证测试文件（`zz_secverify_test.go` ×2，注释写明"临时安全验证测试（评审后删除）"但一直未删除；本次评估期间已清理）。本评估以临时测试逐一复现，**7 条攻击链全部 confirm**：

1. **env/printenv 白名单逃逸**（shell.go:37 白名单含 `env`）：`{command:"env", args:["touch","<path>"]}` → `exec.CommandContext(ctx,"env","touch",...)` 实际执行 `touch`。白名单校验只查 `command` 首词，`args` 路径（shell.go:256-261）不进任何检查 → **任意命令执行**。
2. **args 数组绕过元字符过滤**（shell.go:164-167 只检查 command 字符串）：`args:["sh","-c","echo INJECTED$(id -u)"]` 实测 stdout 返回 `INJECTED501` → **命令替换执行**。
3. **filesystem write → shell python3 RCE 链**（filesystem 写入不审内容 + 白名单含 `python3`）→ **任意代码执行闭环**。
4. **黑名单模式绕过**（shell.go:16-27 子串匹配）：`rm -fr`（flags 重排）不在 blockedCommands → **文件删除成功**。
5. **Shell 无路径禁锢**（shell.go:218-224 只校验 workdir）：`cat /etc/passwd`（cat 在白名单）→ **filesystem 工具的 rootDir jail + symlink 防护 + 敏感文件保护被同注册表的 shell 一句 `cat` 废弃**，AGENTS.md §8 宣称的 FilesScope 权限在实际对抗中失效。
6. **scope 提取 fail-open**（executor.go:127-134, 306-370）：`extractPathFromArgs` 只识别 6 个固定 key、只看顶层、只取第一个；实测 `filePath`、`file`、嵌套 `{"request":{"path":...}}`、MCP 风格 `{"input":{...}}` 全部返回空 → **executor 层 ScopePolicy 检查被静默跳过**。
7. **敏感文件模式缺口**（filesystem.go:25-45）：`authorized_keys` 不在 sensitivePatterns（实测可读）；`filepath.Match` 大小写敏感，`.ENV` 绕过 `*.env`（实测）。

**影响面**：框架自身的威胁模型（guardrail 注入检测、红队 prompt-injection×180）明确假设"agent 可能被 prompt injection 控制"。在此模型下，被注入的 agent 调用默认工具包即可拿到宿主 shell 与任意文件读写。这与 AGENTS.md §2.3 INV-0"宿主零执行 agent 生成代码"的**精神**直接冲突——白名单收录解释器（python3/node/go）与进程派生器（env/find/ln）使白名单形同虚设。

**修复**：① `args` 路径与 command 字符串走同一套校验（最终 argv 全部元素）；② 白名单移除 env/printenv/find/python*/node/go/make/cargo/rustc/git 等可派生进程条目，或加参数级白名单；删除 `WithBlacklist`；③ Shell 执行前对命令 token 中的路径参数统一过 `security.Sandbox.ValidatePath`，`DefaultToolkit` 的 EnableShell 默认注入 Sandbox；④ `extractPathFromArgs` 改完整 JSON 递归遍历 + 全 key 集合，无法解析时 **fail-closed**；⑤ 清理两个遗留工件。

#### P0-2 `jsonutil.Marshal` 返回切片与 pool buffer 别名 → 97.8% 并发请求体被覆写

`internal/jsonutil/pool.go:66-84`：`Marshal` 返回 `buf.Bytes()` 切片后**又把 buffer Put 回 pool**（注释自称"数据直接转移给返回值避免 copy"却又归还，自相矛盾）。buffer 归还后，任何其他 goroutine 的 `Marshal` 都会 Reset+Encode 覆写同一块内存。

**实证**（2000 次并发 Marshal，全部结束后统一比对——即真实使用模式：provider 序列化请求体后交由 HTTP 传输异步读取）：**1955/2000 = 97.8% 请求体被另一请求的内容整体替换**。

**影响面**：所有 Provider 的请求体（`bytes.NewReader(bodyBytes)`）都走此路径。AgentPool 多 agent 并发共享一个 Provider 时：API 收到错误模型/错误消息的 JSON（正确性 bug：400/错误响应），也是**跨会话数据泄漏**（A 会话的 prompt 随 B 的请求发出）。这是本次评估中影响面最大的单个缺陷——100% 请求路径、并发即触发。

**修复**（二选一，建议 a）：(a) 返回前 `out := make([]byte, len(result)); copy(out, result)`（放弃该微优化，收益本就 <5%）；(b) 不 Put 回 pool，把 buffer 所有权转移给调用方（需改全部调用点释放约定）。

#### P0-3 `AnthropicProvider.Complete` 空指针 panic（公开 API 可达）

`anthropic_provider.go:363-372`（`buildStructuredOutput` 第 364 行无条件解引用 `rf.JSONSchema`），调用点 :74-78。只要 `req.ResponseFormat != nil` 且 `JSONSchema == nil`（OpenAI 生态最常见的 `json_object` 模式）即崩。OpenAI（request_types.go:51）和 Gemini（gemini_provider.go:485）均有判空，唯独 Anthropic 没有。

**实证**：`p.Complete(ctx, &CompletionRequest{ResponseFormat: &ResponseFormat{Type: ResponseFormatJSONObject}})` → `PANIC: runtime error: invalid memory address or nil pointer dereference`。一个坏参数让进程崩溃而非返回 error。

**修复**：入口加 `if rf == nil || rf.JSONSchema == nil { ... }`；补回归测试。

#### P0-4 12 个测试文件被 `//go:build ignore` 禁用，167 个 Test 从不运行且已腐烂

`internal/agent/` 下 12 个测试文件（group_chat_test.go、collaboration_test.go、eval_test.go、lifecycle_state_test.go、session_test.go、multimodal_test.go、multimodal_adapter_test.go、discovery_api_full_test.go、distributed_test.go、distributed_integration_test.go、http_transport_api_full_test.go、tcp_transport_api_full_test.go）首行均为 `//go:build ignore`。架构评审将其复制到临时包剥掉标签后 `go vet` 实证：符号重复冲突（TestHandoff_* 与 orchestration_pipeline_test.go）+ `undefined: mockAgentForOrch`——**文件是被"关起来"而非修复，现已腐烂**。

**后果**：① 81.8% 覆盖率是幸存者偏差——collaboration/eval/session/multimodal/discovery/transport 实际覆盖为 0%；② **GroupChat/Debate/Session 等编排路径无任何有效测试保护**，直接违反 AGENTS.md §5 TDD 强制；③ CI 全绿掩盖了这一点（ignore 文件不进编译）。

**修复**：删除 ignore 标签，修符号冲突（重命名重复测试）与缺失 mock，把 167 个测试纳入 CI。这是让"覆盖率达标"恢复可信度的前提。

### 4.2 🟠 P1 — 设计与正确性缺陷

**llm 包**：
- **缓存键语义错误 + 修复未接线**（cache_memory.go:482-512）：`CachedProvider` 只用"最后一条 user 消息"做键，忽略 model/temperature/system prompt/历史/工具集 → 不同上下文**假命中**返回错误响应。生产使用点 capability_agent.go:292、chain_api.go:121（minScore 0.8）。修复函数 `cache_enhanced.go:187-196` 的 `GetRequest`（RequestFingerprint 含 model+全消息序列）已存在但**全仓库无调用**。
- **Stats() 确认数据竞争**（cache_memory.go:337-340 等 3 处）：原子写 + 普通读，`-race` 精确定位；32 位平台有撕裂读风险。
- **ctx 取消误触发熔断**（resilient.go:95-98）：调用方超时/取消累计 5 次即打开熔断 30s——急躁的调用方可拖垮 Provider；`context.Canceled` 未豁免。
- **"共享 transport"名不副实**（transport.go:1-41）：`NewDefaultLLMTransport()` 每次 new，12 个 Provider = 12 套独立连接池，空闲 fd 翻 12 倍。
- **InMemoryCache TTL goroutine 永久泄漏**（cache_memory.go:117-119）：无 Close/Stop；cleanupExpired 不清理 LSH 索引 → 内存无界增长；全局 embeddingCache 无模型/维度隔离 → 64 维与 1536 维向量跨缓存串用，语义搜索永久失效。
- **http.Client.Timeout 掐断长流**（transport.go:36-41 + 120s）：Client.Timeout 覆盖响应体读取全过程，长流式响应超 120s 被中途掐断且上层静默 close(ch) 无错误信号。修复：流式路径改用 ResponseHeaderTimeout + ctx deadline。
- **~880 行复制粘贴**：glm↔qwen doRequest 相似度 1.00（仅名字不同）、Stream 1.00、buildMessages 5 文件 1.00；BaseProvider 已存在但 12 个 Provider 只有 2 个采用，provider_template.go 还在把复制模式固化为新 Provider 模板。任何底座修复（如 P0-2/P0-3）要改 12 处。

**agent 包**：
- **runLoop 早退路径泄露 trace span**（react_loop_core.go:122-124/130-132/186/194）：turnSpan/llmSpan 创建后早退均未 End()，OTel 导出下 trace 永不闭合。
- **resumeFromState 无锁写 a.startTime**（react_lifecycle.go:153/155）与 Stats() RLock 读构成竞争窗口；hookCtx/memSessionID/stats.Status（死字段）同样未纳管。
- **锁顺序注释与实战相反**（react_loop.go:130-133）：文档写 statsMu→runMu，实际唯一嵌套是 runMu→statsMu——文档错误会诱导后续代码制造真实死锁。
- **并行 tool × HITL 挂死**（react_loop_tools.go:54-117 + hitl.go:102-105）：HITLManager 单 pending 槽 + 共享 responseCh，两个 tool 同时请求确认时响应随机送达一个 goroutine，另一方挂起到 ctx 超时（默认关，但属静默错误行为）。
- **异步 goroutine 无界无跟踪**（react_persist.go:131-151）：每条消息派生一个摘要 goroutine，无并发上限、无 WaitGroup；distillKnowledge/saveSolutionMemory/tryDeadlockRecovery 均为无跟踪 fire-and-forget。

**tools 包**：
- **RegisteringCreator 违反 INV-0**（intelligence/registering.go:30-64）：将 LLM 生成 artifact 以 **0755 写盘**并注册为 `sh <path>` 执行的工具——正是 AGENTS.md §2.3 禁止的"宿主写入并加载 agent 生成代码"。当前 dormant（仅测试接线），集成方启用即构成 injection→宿主 RCE。
- **插件安装器**（plugin_installer.go:42-79）：`name`/`version` 未净化即 `filepath.Join`（`../../` 穿越）；**先写盘后验 checksum**；无签名验证（marketplace 有 cosign 但此路径未用）；下载无大小限制。
- **MCP server 暴露面**（mcp_protocol_client.go:428-440,532-586 + mcp/server.go:242-265）：API key 非常量时间比较（timing attack）；`tools/call` 经默认 executor（无 ScopePolicy）可调任意工具含 shell；mcp 子包 MCPServer **完全无认证**；两套实现安全姿态不一致。

### 4.3 🟡 P2 — 其他

- **`go vet` 失败 2 处且 CI 无 vet 门**：cmd/ap/autonomy.go:321 拷贝含 RWMutex 的 GoalPlan（copylocks）；zz_secverify_test.go 未用导入。ci.yml/nightly.yml 均无 `go vet` 步骤，pre-commit 也不查。
- **flaky 测试**：TestMemoryReadback_FastPath ~1% 失败率（异步 fire-and-forget 写库与读取无同步点；覆盖率跑中必现）。
- **pre-commit 钩子可能未激活**：`.githooks/pre-commit` 存在且质量高（5 项检查），但 `git config core.hooksPath` 未设置。
- **超时无上限**（shell.go:198-207、web.go:115-124、api.go:125-134、code_execution.go:99-108）：用户可控 `timeout` 无 clamp，`int(v)` 大值可溢出 Duration。
- **filesystem TOCTOU/健壮性**：openAndValidate（:110-144）先 open（O_TRUNC 截断 symlink 目标）后校验；listDir `info.Size()` 可 nil panic；searchInFile stat→ReadFile 竞态可 OOM。
- **HTTP 工具连接泄漏**（web.go:244-265 等）：每请求新建 Transport 从不 CloseIdleConnections。
- **SSRF 残留段**（web.go:229-242）：遗漏 CGNAT 100.64/10、192.0.0.0/24、198.18/15、240/4 及 IPv6 6to4/NAT64（169.254 元数据地址已正确拦截）；`WithAllowPrivate(true)` 一键关闭防护。
- **流式 goroutine 背压**：anthropic/gemini/qwen/glm/mistral/cohere/ollama/azure 的 `ch <- chunk` 只 select ctx.Done()，消费者停止读取且 ctx 无 deadline 时永久泄漏；openai 的 5s 背压选择静默丢 chunk（内容损坏）。
- **MCP stdio 健壮性**：Scanner 默认 64KB 行上限使超长响应下 readLoop 静默退出、请求全挂死；stdio 子进程继承完整 os.Environ()（含宿主密钥）；配置文件篡改 → StartAll 任意命令执行。
- **data_tools.go**：CSVTool os.Open/os.Create 任意路径读写（无 jail/scope/敏感保护）——又一条绕过 filesystem 全部防护的路径；CSV 公式注入未消敏。
- **ecosystem 示例直依赖 internal/***：文档已自认的技术债务（AGENTS.md §4.2）。
- **模块路径不可 GOPROXY 解析**：`agentprimordia` 首段无点号，`go install` 不可用（README 已诚实说明）。
- **agent 包 97.8K 行**：runLoop（327 行/cc≈45）与 reactLoopEngine（192 行/cc≈31）为全仓圈复杂度集中点；流式模式每轮双倍 LLM 调用且 Usage 丢失；重试不区分瞬时/永久错误；文档 3 处引用不存在的 `NewReActAgent` 构造函数；capability 三处存储 + 双份 WithXxx 实现。
